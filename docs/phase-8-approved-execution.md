# Phase 8 approved execution contract

Implemented October 30, 2026 for the single local synthetic merchant. Gate evidence belongs in the [Phase 8 handoff](handoffs/phase-8.md). No live adapter, platform credentials, network advertising call, optimizer or later module is implemented.

## Requirements and defaults

Accepted requirements are A12-A17, explicit approval for every simulated advertising mutation, durable exact resource/INR/evidence binding, expiry, locks, idempotency, revalidation, read-back, partial/unknown outcomes, approved recovery, kill switch, current reviewed mappings/capabilities and inventory/diagnostic precedence. Infrastructure/API charges remain INR 0. The 30-minute proposal lifetime and conservative global serialization are implementation defaults, not individually merchant-confirmed settings. Actual UTC controls expiry and freshness; fixture time cannot extend consent.

Authenticated POST `/api/actions/propose` accepts an operator's exact pause, resume, unshared inventory throttle, two-budget transfer or inverse partial-transfer recovery. No recommendation grants consent. Earlier reporting/recommendation `mutation_enabled=false` flags describe those read-only modules; this separate approved simulator does not turn them into live write adapters. Each proposed plan retains exact platform/account/resource kind/ID, currency INR, integer paise or status, expected simulator value/revision/last request, reviewed products and mapping evidence, complete budget members/capabilities, six input publication IDs, reason and SHA-256 digest. Creation performs no advertising mutation. It initializes missing simulator observations from the current synthetic ad source without overwriting existing state. Imported inventory prior-pause claims never enter execution history.

Approval is a separate POST `/api/actions/{id}/approve` with `approve=true` and the displayed exact digest. The existing single authenticated operator is the approval actor; no multi-user identity or separation of duties is claimed. Consent and timestamp persist in PostgreSQL. Authenticated POST `/api/actions/{id}/reject` rejects an unexecuted proposal or withdraws its pending approval under the execution lock, retaining the earlier consent in audit. It never compensates completed writes; the kill switch governs new in-flight mutations. Duplicate identical proposals reuse the durable client key; conflicting reuse rejects. Duplicate approvals/execution do not add mutations. Every new recovery needs its own exact proposal and approval.

## Scope and revalidation

Execution takes the same commerce/ad/attribution/finance/inventory/diagnostic import locks plus a single merchant execution lock. Locks serialize writers across processes and pin dependencies. Each mutation has a unique persisted request ID. Unknown intents reserve the exact target, affected budget and whole-member scope across connection/process exit until read-back resolves them, including overlap between status and budget requests. No blind resend occurs after an executing/unknown plan is resumed: reconciliation only, followed by a terminal partial/failed/succeeded or continued unknown outcome. Unattempted changes require a new proposal.

Before execution and before each mutation, real Exasol supplies verified ad capabilities, mapping evidence, inventory features and diagnostic checks. All current publication IDs must be coherent and match the approved IDs. Ad/inventory/diagnostic source observations must be within 900 seconds; affected variants must independently remain fresh under inventory policy. Historical commerce/finance cutoffs remain historical context; a current observation does not refresh them. Exasol unavailable/corrupt evidence blocks dependent new writes. Operational configurations never substitute for analytical features.

Every exact status target needs supported status control and a resolved current reviewed whole-resource mapping. A protective pause requires every mapped product to qualify; mixed unaffected products cannot broaden pause. A throttle requires every mapped product to qualify for throttle, a supported unshared exact budget and a strictly smaller integer-paise value. Protective pause can reduce delivery despite a destination issue, but still requires available coherent diagnostic evidence. All source resource blockers/freshness apply. Resume, transfer and inverse recovery require clear fresh stock and cleared exact-member diagnostics/catalog conditions; missing destinations withhold growth. Budget requests address a distinct budget ID: Meta resolves its actual owner; Google resolves all shared members. Every member needs its own exact valid reviewed mapping and cleared evidence. Product controls and parent mapping inheritance are never invented.

The approved digest also binds `clock_valid_until`: the earliest source/affected-stock/resource/destination freshness boundary, selected-offer expiry or next mapping validity transition. The final PostgreSQL update checks actual `clock_timestamp()` against this proof deadline and approval expiry atomically. Slow analytics, queueing or adapter delay cannot renew evidence; the executor rejects proof that expires during revalidation. Execution conservatively requires remaining time before the proof boundary even when a read-only freshness snapshot is exactly at its inclusive 900-second limit.

Before values include revision and last request, so editing away and back invalidates a plan. Resume additionally requires a durable succeeded, approved pause step whose request ID/revision is still current. Imported AdVergent/merchant/unknown paused state cannot grant this. Recovery requires the exact succeeded portion of a partially succeeded original transfer, unchanged state and exact inverse values. It cannot overwrite a later merchant edit or recover advertising already spent.

## Simulation, failure and audit

Migration 008 keeps immutable application-created plan terms, approval identity/time, separate step intents, external-state stand-in, unique receipts, read-back values, errors, events and kill switch in PostgreSQL. Exasol-specific SQL remains in existing analytics adapters. No extra analytical store or provisioning is introduced.

Simulator apply is a separate transaction from intent and read-back. It checks executing approval, exact intent, real expiry, expected revision and kill-switch row lock before changing anything, and commits the state change and unique receipt together. This local atomic simulator contract is not a claim of external API atomicity or fidelity. Executor audit retains request ID, before/after/revision, actual read-back, actor, timestamps, digest/evidence and sanitized error codes.

Simulator changes never rewrite immutable report sources or historical spend. Source budget metadata retains its observation cutoff; ledger step read-back shows actual simulator values. Subsequent proposals inspect that durable simulator state rather than resetting it from reporting.

Transfers require two different budgets: donor first, strictly smaller; recipient second, larger by exactly equal integer paise. Different percentage changes are expected. Donor read-back must succeed before recipient mutation. The recipient transaction also locks and verifies every earlier successful target at its exact post-write revision/request, so a merchant edit after donor read-back stops the recipient. A failed recipient exposes actual unchanged recipient and changed donor budgets as `partially_succeeded`. A timeout after commit requires read-back; matching value/revision/request resolves success without resend. Unavailable/conflicting read-back stays `unknown`, stops all remaining steps and reserves resources. Reconciliation remains possible with kill switch enabled, expired consent or unavailable analytics because it reads state only.

Kill switch updates are authenticated, durable and audited. Its row lock orders each apply against switch activation: after activation commits, no subsequent mutation can pass. It does not undo a mutation already committed. Toggle, read-only reconciliation and approvals do not authorize new writes. Expired or changed approvals reject; a new plan is required. Operational database failure returns sanitized 503 and cannot fall back to in-memory authorization.

## User interface and evidence levels

The approved-execution region exposes exact structured proposal inputs, INR amounts, displayed plan terms/scopes/pins, separate explicit approve and execute controls, expiry, partial/unknown/failed statuses, actual step outcomes and audit, plus kill switch. React escapes all text. UI/API authentication and same-origin POST protections apply. Default historical publications stay stale and prevent proposals; synthetic acceptance sources explicitly create new observations under isolated resource IDs.

Isolated policy tests, real PostgreSQL/Exasol tests, authenticated browser flows and actual stopped-Exasol tests are distinct evidence. Fixture preparation only imports synthetic source observations; it grants no approval and makes no advertising mutation. Acceptance tests explicitly approve each executed plan and retain action history. Default publications are restored afterward. Production hard-kill/reboot recovery, scale, retention/cleanup, live capability/state fidelity, multi-user approval, credentials and model effectiveness remain unverified.
