# Phase 10 breakout contract

Implemented October 31, 2026 for the single synthetic local merchant. Acceptance is A19: a few clicks never imply high confidence or a precise budget forecast. Exact executed evidence belongs in the [Phase 10 handoff](handoffs/phase-10.md). No publishing, advertising mutation, paid provisioning or later module is authorized; INR 0.

## Requirements and labelled defaults

Accepted scope: synthetic funnel signals, explicit coverage, deduplicated events, breakout ranking, inventory readiness, minimum evidence and time-based evaluation. Demo defaults, not merchant-calibrated or statistically significant settings: adjacent half-open seven-day baseline and signal windows, then a separate seven-day evaluation window. Each baseline/signal requires 100 views, 20 add-to-carts, 1,000 impressions, 20 clicks and seven supplied tracking days. Ad placement/series identity must match across baseline and signal. Missing coverage is unknown, never a zero-event assertion about merchant behavior. Coverage describes synthetic tracking assertions, not live source completeness or individual users/sessions. Cart/view and click/impression counts must be consistent.

The [source generator](../backend/advergent/breakout_fixture.py) emits raw event deliveries and coverage assertions, not computed dashboard results. The [strict source model and policy](../backend/advergent/breakout.py) reject conflicting event IDs, duplicate coverage, unknown fields (including event revenue), naive timestamps and evidence after source observation. Timestamps normalize to UTC. Exact repeated event IDs collapse once; distinct events remain distinct even for the same product/time. Repeated purchase callbacks additionally collapse to distinct existing order/product pairs within each window. Purchase references must match an actual purchased product in the pinned commerce lines and cannot predate order placement. They are observations only: **added revenue is always zero**. No funnel event, platform claim, warehouse counter or foundation fixture is added to commerce/finance revenue. Multi-product purchase pairs are contextual counts, never independently summed orders.

Each product exposes baseline/signal/evaluation counts, tracked days, view growth, cart rate, comparable CTR, nullable historical expected contribution margin, current inventory risk, blockers, score and rank. View growth bps = (signal views - baseline views) / baseline views × 10,000. Cart rate and CTR use their own denominators; zero denominators remain unknown. Integer bps round down. Historical margin = complete pinned purchased-product expected contribution before ads after reserve / positive net delivered sales × 10,000, including failed-order costs. Missing required costs, absent/zero net sales and negative margin abstain; a covered subtotal never becomes complete margin. Current catalog COGS never replace historical financial costs.

Eligible descriptive score = min(10,000, positive view growth bps) + cart rate bps + CTR bps + nonnegative historical margin bps. This equal-basis-point weighting and growth cap are arbitrary uncalibrated defaults. Stable ties use product ID. Positive view growth, all evidence floors/coverage/comparability, coherent pinned publications and **clear, fresh inventory** are required. Stockout, size risk, low cover, unknown lead/demand and warnings block ranking through the established inventory policy. No receipts are added to sellable stock. Sparse, stale or incomplete products have null score and null rank; raw historical evidence remains visible. Missing products in the funnel coverage do not disappear from the catalog.

Actual UTC controls query freshness: source observation and signal cutoff must each be no more than 900 seconds old and not in the future. Default historical fixture observations remain stale after replay. Changing source observation alone cannot refresh an old signal. Historical commerce/finance/ad cutoffs remain visible context; a fresh funnel/warehouse observation does not renew them. This is product-signal ranking, not an advertising-resource recommendation: native ad hints do not create reviewed mappings, no resource scope/capability or budget control is invented, and no recommendation enters the executor.

## Time-based evaluation and limitations

Exasol counts baseline [signal end -14 days, -7 days), signal [-7 days, signal end), evaluation [signal end, +7 days). All are capped by source observation and query time. A boundary event enters only the later window. The later window never contributes to the score, ranking thresholds or weights. Evaluation stays pending until its entire window closes under both query and source observation clocks. Insufficient baseline/signal evidence, inconsistent counters, missing seven-day coverage or fewer than 100 evaluation views/20 carts yields insufficient; otherwise sustained means views at least equal signal views, else not sustained. This label is a separate descriptive follow-up, not predictive accuracy, calibrated confidence, causal lift or incremental profit. No model is trained, threshold selected on holdout, probability emitted, spend-to-sales response fitted or budget forecast returned. Current inventory and full pinned historical finance context make this a current eligibility screen, **not a historical portfolio backtest**. Historical evaluation never revives a stale rank.

## Storage and interfaces

[BreakoutSQL](../backend/advergent/breakout_sql.py), composed into [ExasolAnalytics](../backend/advergent/exasol.py), owns all Exasol-specific SQL. Explicit `worker migrate` creates BR_EVENTS and BR_SOURCES. The bundled complete synthetic source is content-addressed by SHA-256 over canonical validated input, cached transactionally in Exasol on first authenticated query and fully verified against typed rows on every read. A failed insert does not commit a completion marker; retries reuse only fully verified sources. There is no new operational publication pointer, migration in PostgreSQL, CLI importer, browser source editor, cleanup or action state. The bundled fixture is the selected source; old analytical versions remain retained. This small bounded fixture cache is not a live ingestion architecture or concurrent high-volume service guarantee. An overlapping first-load transaction may fail closed and require a read retry.

Actual Exasol groups deduplicated event facts, joins purchase order/product references to commerce, and provides verified pinned inventory and financial inputs. Policy applies vendor-neutral score and abstention rules. PostgreSQL retains existing immutable operational configurations/publications, authentication and untouched action history. No analytical fallback exists. Typed/source corruption or Exasol outage suppresses all current breakout data.

Authenticated GET `/api/breakout` pins the inventory's exact finance, commerce, ads and attribution identities. Before-query coherence and after-query pointer checks invalidate every rank on change. The response exposes five pins, matching source cutoffs, source hash/version/observation, window bounds and query time. [Breakout UI](../frontend/src/Breakout.tsx) escapes evidence, clears previous results on query/failure, displays unranked blockers and a separate later evaluation, and exposes only a read-only query button. No mutation/publishing flag can become true.

Generate the deterministic source with `.\.venv\Scripts\python.exe -m advergent.breakout_fixture`; apply explicit analytics schema setup through `worker migrate` after loading the existing private environment. Do not regenerate source timestamps to disguise staleness. Source-changing real-store checks run sequentially with healthy Exasol, restoring defaults in `finally`. Exclude mutation-performing execution integration/browser cases. Preserve TLS/private/launcher/deployment/volumes and the entire action ledger during actual outage checks.
